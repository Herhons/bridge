## 二、Gemini 的整合（原文见 `gemini_summary.md`）

共识四条：桌面三对 choose/use 去重；补 `reject` / `lastreply` 的离线用例；收敛大文件与循环依赖；核心防御机制（Gemini 专用实现、子进程调用、高入度基础模块、unknown 阻断重发）保持不动。

五处分歧及裁决：

1. 先核查状态机边界还是先去重 → 裁决：先核查，再去重。理由是"重试导致重复发送、超时后子进程继续抢鼠标"属于运行时隐患，去重属于维护成本。
2. 是否拆 `ui.lock` 做流水线并发 → 否决。物理焦点与剪贴板全局唯一，拆锁会破坏 sendgate 的前台指纹假设。
3. CI 形式 → 本地 pre-commit 先行，托管到 GitHub 再补离线 Action。
4. Python 3.10 升级 → 不纳入近期。
5. 是否把 Gemini 塞回 `flow.py` → 不塞。

最终清单：P0-1 收紧提交重试 / 超时强杀 / 幂等键作用域；P0-2 补 `reject`、`lastreply`、`desk_sites` 的离线测试并加门禁；P1-1 抽桌面端共享流；P2-1 解循环依赖、拆大文件。

## 三、我的判断（不照抄）

**认同并要立刻做的**

- **P0-1 的"3 秒重试可能二次发送"是真问题。** B19 里那段重试是"清草稿 → 重写 → 重提交"；如果第一次点击其实已经提交、只是页面还没渲染出提问块，就会真的发两遍。这条我认，而且它正是我自己写的。
- **P0-2 补测试**：`reject` 与 `lastreply` 在失败判定与兜底采集的关键路径上，零覆盖确实不该。成本低，先做。

**认同但要排后面的**

- **P1-1 抽桌面端共享流**：方向对，但三对副本现在跑得稳，去重的回归面比收益大；等 P0 落地、测试补齐之后再动，且只抽 `choose`（无发送副作用）。

**不同意的**

- **"拆 `ui.lock` 做四端并发生成"（gemini 提的）**：不做。B19 前实测过 `endpoint_concurrency=4`，四端抢同一把锁的直接表现是"窗口提不到前台"与整轮超时；后台标签页还会被 Chrome 节流。串行是这个系统的正确形态，不是妥协。
- **"先做 CI"**：不按云端 CI 走。这套东西全靠 Windows UIA，云端跑不了真机；1476 个用例离线可跑，本地 pre-commit 就够，云端只是摆设。

**存疑、需要实测再定**

- **"幂等键要含 purpose"**：现在键只有 `sha256(prompt)`，同一问题换档位会被旧记录挡住。这是真实不便，但改键会动到 278 条既有账本，需要一次迁移；先记下来，不动。

## 四、我准备怎么做（按顺序）

1. **修 gemini 的重试语义**：3 秒无落点证据时，只做"清草稿 + 重写"，**不重提交**；把"已点击过"记进 state，第二次点击必须同时满足"账本里没有 accepted/submitting"且"页面上确实没有提问块"。加两条离线用例：点过但页面没渲染 → 不重发；确实没点出去 → 重发一次。
2. **补 `reject` / `lastreply` 的离线用例**：用 `evidence/` 里现有的真实树快照做 fixture，覆盖"限流 vs 终态拒绝"与"半截回答 / 上一轮旧回答"两类。
3. **加本地门禁**：`pre-commit` 跑全量离线用例（10 分钟内），失败即拒提交。
4. **之后再评估去重**：只抽 `choose`，按 dsh → codex → opencode 逐对迁，每迁一对跑全量。
5. **不做**：拆 uilock、把 gemini 塞回 flow、改子进程为线程、升级 Python、动幂等键。
