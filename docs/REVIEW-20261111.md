## 二、逐条核对结果

### 成立（可直接改）

**1）账本会被后来的 busy 读降级 —— ChatGPT 第 1 条，已核实**

`conversation.ask()` 第 1934 行**无条件**调 `ledger.finish(result)`；而 `conversation_busy` 在 `_RETRYABLE_STAGES` 里（`:1788`），`finish()` 会把它写成 `failed_retryable`。`submissions.finish`（`:566`）只要记录存在就覆盖，没有「不许把 accepted 降级」的保护。

后果：同一 `(endpoint, prompt)` 先成功（accepted）→ 之后再调一次、恰好首读 busy → 账本变 `failed_retryable` → 而 `pending()` 不拦可重试态 → 第三次调用会**真的再发一遍**。这与会审追求的 fail-closed 正好相反。

**2）桌面端只有 workbuddy 没接账本 —— Grok 第 1 条 / Gemini 第 2 条，核实后范围缩小**

会审说「桌面四端全部绕过」，实际不是：

- `codex_use` / `dsh_use` / `opencode_use` 各自有 `ask()`，都接收并透传 `purpose`（`codex_use.py:1562`、`dsh_use.py:1015`、`opencode_use.py:1133`），也调了 `tier_guard.gate`；
- `desk_flow.ask/cli` 在 `src/` 里**没有任何调用方**（只有 `desk_sites.py` import 它的 `DeskSite` 数据类），会审是照着它的签名做的推断；
- 真正的缺口是 **workbuddy**：`--purpose` 虽必填，但 `workbuddy.ask`（`:1101`）调 `send_and_wait(conversation, prompt, 0.0, **options)` 时只传了 `pre_send`，没把 `purpose` 传进 `conversation.ask`，所以账本未启用。

一处修正：Grok 说「完全绕过 sendgate」不准确——`conversation.ask` 内部仍调 `sendgate.page_stamp/page_confirm`（`:1247/1278`），被绕过的是**账本**。

**3）`submission_count` 恒为 1 —— Gemini 第 3 条，**核了是设计误解，不改****

`_validate`（`submissions.py:355`）明确要求：`submission_count` 只能是 **0 或 1**（draft/failed_retryable 为 0，其余为 1），它是「这条记录有没有提交过」的布尔式不变量；重试历史记在 `attempts` 里。把它改成 `len(attempts)` 会当场违反不变量（校验直接抛 `submission_count_invariant`）。我试改了一次，被 `_validate` 拦住，已回退。

### 不成立（会审看错了）

**Gemini 第 1 条 / DeepSeek 第 1 条「`flow.py:347/354` 少写 `**`，会 TypeError」—— 不是它们看错，是我材料坏了。**
真实代码是 `return {**result, "stage": "no_window"}`，`**` 在。问题出在我给它们的材料：去 Markdown 的脚本里有一句 `.replace('**','')`，把 Python 的字典解包也一起删了，喂进去的源码变成 `{result, ...}`。两家都据此报了同一个「必崩」——判断完全合理，是输入被污染。
**教训**：给模型的代码材料只能处理行首标记与表格，绝不能做全局的 `**`/反引号替换。

**Gemini 第 7 条 / B20 会审「`reject.py` 零覆盖」—— 不成立。**
`tests/test_r11_reject_signals.py` 有 33 个用例；B21 补的是 `desk_sites`（当时唯一真零覆盖的模块）。

**ChatGPT 第 6 条「坏账本反而放行」—— 不成立。**
`normalize()` 对未知状态一律归一到 `STATE_UNKNOWN`（`:109` 的 else 分支），`pending()` 见 unknown 即拦；不会出现「归一失败 → 放行」。

## 三、整改（已执行，2026-11-11）

### P0-1 账本不许被降级 ✅ 已改

`src/qi/conversation.py`：`_Ledger` 增加 `reserved` 标志，`reserve()` 成功才置真；`finish()` 在「可重试阶段 且 本轮没落账」时直接返回，不写账。
`src/qi/submissions.py`：`finish()` 增加不变量——旧记录是 `accepted`/`unknown` 时，拒绝写成 `failed_retryable`（直接 return，不写盘、不写 `scope_after`、不动 `updated_at`）。判据用**旧状态**，所以本轮 `submitting → failed_retryable` 照旧放行。

新增 `tests/test_b24_ledger_no_downgrade.py`（10 条）：accepted 记录遇 busy 收尾后**字节不变**、`pending()` 仍非空；reserve 过的失败仍变可重试；拦发路径不改状态。

### P0-2 workbuddy 接入账本 ✅ B26 已解决（B24 时曾回退）

B24 把 `purpose` 透传进 `workbuddy.ask` 之后，`test_rework09f_recovery` 与 `test_rework06b_presend` 变红，当时判定为「R7 语义冲突」并回退。B26 复查发现**真实原因是双重 reserve**：`_last_gate`（`workbuddy.py:1258`）发送前已经 `submissions.reserve` 落过账，`_Ledger.reserve` 又读一次 `pending()`，把**本轮刚写的** `submitting` 当成"上一次"，把合法首发自己拦掉。

改法是「单一 reserve 归属权」：`_last_gate` 在返回值里加 `reserved=True`；`conversation.ask` 见到它就跳过自己的 `reserve`，改调 `_Ledger.adopt()`（只置 `reserved` 标志，不读账本）。于是 reserve 仍只发生一次（带 hwnd 的那次），R7 的三条断言**一行没改**，两条用例原样通过。

新增 `tests/test_b26_workbuddy_ledger.py`：门禁已落账时首发不被自己拦、第二轮被账本拦住（一个键都不敲）、不给 `purpose` 时入参逐字节不变。`test_card06d` 只补了 3 处桩签名。

### P1-1 `submission_count` ❌ 已否决

`_validate` 要求它是 0/1 的布尔式不变量，改 `len(attempts)` 会当场抛 `submission_count_invariant`。试改后被校验拦住，已回退。

### P0-3 提问已在树上就不许再点发送 ✅ 已改

`conversation.py` 的 `_maybe_retry` 增加一条前置判据：`len(prompt_nodes(view, prompt)) > sent_prompts` 时直接返回。提问渲染出来 = 这一下确实发出去了，比"框非空"更硬。
新增 `tests/test_b25_no_resend_when_prompt_present.py`：旧代码 `submits == 2`，改后 `== 1`；同时保留"提问确实没出现 → 允许重试一次"的正向用例。

### P0-4 chatgpt 提前交卷必须先证明同一会话 ✅ 已改

`conversation.py` 里把 `watch(view)` 移到 `sid` 计算之后，且只在 `send_sid is not None and sid == send_sid` 时调用。发车前记下 `send_sid = session_id_of(before.url)`；拿不到会话 id 就不提前交卷，退回正常等待。
新增 `tests/test_b25_watch_identity.py`：切到 `/c/bbb` 时旧代码会早退 `answered`，改后不早退；同一会话仍能提前。

### P0-5 HTTP `/workflow` 与 CLI 共用证据不变量 ✅ 已改

`workflow.py` 抽出纯函数 `check_move(record, target, missing)` 与 `next_repair_id(cards, card)`；CLI 的 `move` 与 `server.Engine.workflow_move` 都调它。HTTP 不再清空 `missing`，`block` 也会建 `parent` 修复子卡，响应里带 `repair_card`。

### B27：把「不做」的三条重新拆了一遍

上一轮把三件事笼统写成"不做"，其中两件其实是**该做没做**。重新处置：

| 原结论 | 现在怎么做 | 结果 |
|---|---|---|
| 扩 `reject.PROFILES` | **不打开判据**（缺真机证据，打开就是猜），但把每轮看到的**结构事实**带进结果与 job 证据：`reject.signals()` 产出 `echo_back / send_disabled / accepted_no_activity`，挂在超时结果与 `_run_use` 的 detail 上 | 攒证据的通道打通了，`test_b26_reject_diagnostics.py`（5 条） |
| 自动降级 `unknown` | **仍然不做，但给出了可执行出口**：`submission_audit.py` 新增 `blocked` 列表（只列 `unknown / failed_terminal / submitting`，不列正常的 `accepted`），每条带年龄与**可直接复制**的解锁命令 | `test_b26_audit_blocked.py`（3 条） |
| 放宽 `request_id` 幂等 | **不做自动放宽**，改成**显式重试**：`POST /ask` 带 `retry: true`、且旧 job 是 `interrupted_by_restart` 时才新排一条，旧记录标 `superseded_by`，`_find_request` 只认未取代的那条 | `test_restart_recovery.py` 增加 3 条 |

**为什么自动降级 `unknown` 仍然做不到**：`unknown` 的字面含义是"上次提交状态不明"。进程可能死在 `submit()` 之前（没发），也可能死在之后（发了）。账本只记录"已 reserve"，无法区分这两者；而页面只能证明"有"，无法证明"没有"（提问可能被折叠、滚动、换会话）。任何仅凭超时的自动降级都会把"可能已发"变成"再发一次"，代价不可逆。所以只保留显式人工出口，并且强制要求 `--state unknown --reason --confirm` 三件套。
