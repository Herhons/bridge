§8 材料投喂 / §5.2 Round 0
「网页端上传是循环的必备能力，须在 Round 0 修通，并有一次通过的自检验证「文件已落到该端、对方按文件内容作答」。」
问题：Round 0 同时要求「用完整管道审本规格」且「必须证明上传可用」。但上传自检依赖真机网页端，而建造阶段明确「不强制真机一次跑完四席」。若上传路径在 Round 0 前未稳定，则 Round 0 无法同时完成「审规格」与「证明上传」，循环卡在入口。
失败：编排器干跑通过后进入 Round 0，因上传未通而无法产出「真读」意见，停机条件 4 触发，Round 0 无法出口。
改：把「上传自检通过」列为 §5.1 进入条件的硬前置（用夹具或单席冒烟记录），Round 0 只负责用已通的上传路径跑完整管道，不再把「修通」和「证明」绑在同一轮。
验收：离线测试断言「upload 配置且自检未通过时拒绝开 Round 0」；干跑用已标记通过的上传夹具能产出 quote_check。
§5.3 引用验真（Round 0 变体）
「真读 = 命中 ≥ 3 且命中率 ≥ 0.7，且至少一条落在 docs/self_iteration_spec.md。分段粘贴时，命中以「章节号 + 逐字引句」为准」
问题：规格审与代码审共用同一数值阈值。规格文本短、章节少，5–8 条意见很容易因「只引了 2 个章节」被判未读，即使内容完全命中。§9.1 又允许「章节号或行号对上快照文本」算命中，与「≥3」冲突。
失败：四家都认真审了规格，却因阈值过高全部 partial/未读，汇总空转，停机条件 1 误触发。
改：Round 0 单独阈值（例如命中 ≥2 且命中率 ≥0.6，且至少一条落在本规格），并在 quote_check.py 用测试锁死「规格核心路径」与「代码核心路径」两套规则。
验收：用 2026-11-11 夹具 + 本规格夹具分别断言真读/未读判定；空白归一测试覆盖章节号+引句。
§10 计划闸门 / §5.4 修订什么
「若意见要求改变轮次合同（阶段、闸门、停机条件、评审厂商集合、匿名规则、授权边界），属于大改，必须先得到 Herhons 点头」
问题：Round 0 的目的就是审本规格并可能修订合同条款，但闸门把「改合同」一律列为大改。编排器在 Round 0 产出计划后必须停等人工，无法在同一轮内完成「修订规格 + 同步编排器」的闭环。
失败：幸存意见要求微调停机条件或四审集合，流程卡在「大改待批」，无法归档 CONTINUE，Round 0 出口条件（§5.5）无法满足。
改：明确「Round 0 内对规格文本的修订（含合同条款澄清）默认小改，除非触碰 PLAN.md 红线或 known_gaps.md 已决定不做项」；真正的合同大改才走 §10 大改定义。
验收：干跑夹具中含「改停机条件措辞」的意见，断言计划分类为小改且允许继续；含「改四审厂商集合」的意见仍判大改。
§12 停机条件 1 / §7.3 有效回复
「会审齐了，验真后没有任何「真读」幸存意见……即停」且「至少 3 家不同厂商给出「真读」……才算齐」
问题：Round 0 是第一次真机跑完整管道，上传/粘贴、网页端稳定性、引用格式都可能不稳定。一次失败即停，没有「Round 0 允许重试一次」的明确出口，与 §5.5「最多再跑一轮 Round 0」的意图不一致。
失败：某家因网页端临时不可用未达真读，三家凑不齐，直接 STOP，无法进入 §5.5 的 round-0b。
改：停机条件 1 对 Round 0 例外——未达 3 家真读时允许按 §5.5 开 round-0b（须 Herhons 点头），两次后才强制停。
验收：状态机测试：Round 0 真读不足时写 CONTINUE 到 round-0b；第二次仍不足才写 STOP。
§9.2 匿名 Gemini 汇总 / §2 角色
「匿名包必须做到：去掉厂商名、模型名……」且「汇总本身走 Gemini 网页端」
问题：汇总者是 Gemini，而四审里也有 Gemini。即使去掉名字，Gemini 仍可能识别出自己上一轮的措辞或结构，产生自我回声。规格未规定「汇总 Gemini 不得与四审 Gemini 同会话/同窗口」。
失败：匿名包里仍保留 Gemini 特有的引用风格，汇总者偏袒或重复自己的意见，优先级失真。
改：要求汇总必须用新对话（
workbuddy_use --new
或网页端新窗口），并在匿名包增加「禁止根据措辞猜测来源」的硬指令；归档记录会话 ID 证明隔离。
验收：匿名化测试断言输出无厂商名；干跑断言汇总 prompt 含「新对话」标记且不携带历史。
§4 循环总览 / §13 编排器建造范围
「状态机落盘。进程被杀后能从本轮已完成的步骤续跑，且不违反防重发」
问题：规格要求续跑，但未定义「已 accepted 的提问」在状态机中的持久化格式，也未说明与现有
live_job
/ 账本的对接边界。建造时容易重新实现一套发送状态，违反「不要再复制一套发送栈」。
失败：续跑时重复发送已 accepted 的提问，或状态机与账本不一致，触发防重发红线。
改：明确状态机只记录「步骤完成标记 + 已 accepted 的 job id」，发送语义完全复用现有
；补充状态文件 schema 与恢复测试。
验收：杀进程后从中间步骤恢复的离线测试，断言同一提问不再发送且 quote_check 能续跑。
